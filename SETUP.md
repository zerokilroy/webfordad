# Запуск и деплой

Три части, запускаются отдельно:
- `/` — фронтенд (Vite + React). Сайт + админка на `/admin`.
- `/backend` — API-сервер (Express + Postgres/pg-mem). Приём заявок, авторизация, файлы.
- `/тг бот МТП заявки` — сервис, шлёт заявку в Telegram.

## Как запустить локально

```bash
# 1. backend
cd backend && npm install && npm run build && npm start

# 2. telegram-бот (в отдельном терминале)
cd tg_bot && npm install && npm run build && npm start

# 3. фронтенд (в отдельном терминале, из корня)
npm install && npm run dev
```
Открой `http://localhost:5173`, сайт на `/`, админка на `/admin` (admin / 1234).

## Хранение файлов заявок (чертежи/фото/pdf — любое расширение)

### Как это работает

1. Клиент прикрепляет файл любого расширения к заявке на сайте.
2. Backend принимает файл (без всяких ограничений по типу — только по размеру, 100 МБ) и сохраняет его через `backend/src/utils/storage.ts`.
3. У этого модуля два режима, переключаются переменной `STORAGE_DRIVER` в `backend/.env`:
   - **`local`** (по умолчанию) — файл пишется на диск сервера, в папку `backend/uploads/`. Ничего настраивать не нужно, работает сразу.
   - **`s3`** — файл уходит в S3-совместимое облачное хранилище (Timeweb Cloud, Яндекс Object Storage, Selectel и т.п.).
4. В базе у заявки хранится не публичная ссылка, а внутренний "ключ" файла (`file_key`) — по нему backend потом сам достаёт файл из нужного хранилища.
5. В админке файл **не является публичной ссылкой** — кнопка "Открыть файл" делает запрос с твоим токеном авторизации на `GET /api/orders/:id/file`, backend проверяет, что ты залогинен, и только тогда отдаёт содержимое файла. Так вложения нельзя скачать посторонним, даже если они узнают "ссылку" — без токена админа сервер отдаст 401.

### Зачем два режима, а не сразу облако

- **Локально/на своём VPS** — режим `local` полностью достаточен и ничего не стоит: файлы просто лежат на диске сервера рядом с самим приложением. Именно так стоит тестировать сейчас.
- **На PaaS с "эфемерным" диском** (например, Timeweb Cloud App Platform, где при каждом передеплое файловая система пересоздаётся с нуля) — там `local` не годится: файлы будут стираться при каждом обновлении. Для таких хостингов нужен режим `s3` — тогда файлы живут отдельно от кода приложения и переживают любые передеплои.
- Если в итоге арендуешь обычный VPS (не PaaS с эфемерным диском) — можно спокойно оставаться на `local` даже в проде, просто не забывай делать бэкап папки `uploads/` вместе с базой.

### Про Яндекс.Диск / Google Диск

Технически можно, но я не рекомендую: это сервисы для личных файлов человека, а не для автоматической серверной записи файлов от посторонних (тебе пришлось бы городить OAuth-авторизацию, обновление токенов, разбираться с квотами и API, которые не заточены под "тысячи мелких файлов от анонимных клиентов"). S3-совместимое хранилище — как раз стандартный инструмент именно для такой задачи, API у него в разы проще и стабильнее, и он уже поддержан в проекте (режим `s3`). Если хочешь, чтобы файлы были доступны в удобном виде на твоём личном Я.Диске — можно один раз в день скриптом синхронизировать папку `uploads/` (или бакет) туда, но как основное "боевое" хранилище для сайта — используй S3.

### Как переключиться на S3 (когда будешь брать хостинг)

В `backend/.env`:
```
STORAGE_DRIVER=s3
S3_BUCKET=...
S3_REGION=...
S3_ENDPOINT=...           # для Timeweb Cloud/Яндекса — адрес их S3-эндпоинта
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
```
Код менять не нужно — переключение полностью на уровне `.env`.

## Права админов

- Есть флаг **"Главный админ"** (`admin`, создаётся автоматически при первом запуске) — его нельзя удалить никем и никогда, в интерфейсе он отмечен жёлтым бейджем "Главный админ".
- Любой залогиненный админ **не может удалить сам себя** (свою же текущую сессию) — только другой супер-админ может удалить его аккаунт.
- **Пароли хранятся хешированными** (bcrypt, необратимо) — их нельзя "посмотреть" в открытом виде никому, включая супер-админа. Это не ограничение проекта, а как работают пароли везде, где к безопасности относятся серьёзно: увидеть можно только в момент, когда пароль набирают (при создании/смене), после — только хеш.
  - Каждый админ может **сменить свой пароль** сам (нужен текущий пароль) — раздел "Сменить свой пароль" на странице пользователей.
  - Супер-админ может **сбросить пароль** любому не-главному админу (без знания старого пароля) — кнопка "Сбросить пароль" в списке пользователей.
  - Пароль главного админа может сменить только он сам.

## Где хранятся логины и как их менять

Все логины и хеши паролей — в таблице `admin_users` в базе данных (той же, что и заявки): либо в pg-mem (временно, в памяти, для локальной разработки), либо в настоящем Postgres, если задан `DATABASE_URL`. Менять их напрямую через SQL не нужно и не стоит — всё управление через админку:
- **Создание нового админа** — раздел "Добавить нового пользователя" на `/admin/users` (доступно только супер-админам).
- **Смена пароля** — см. выше.
- **Удаление** — кнопка "Удалить" в списке (не работает на главном админе и на себе самом).

## Авторизация — что было пересмотрено и исправлено

- Раньше `GET /api/orders` (список всех заявок с именами/телефонами/email клиентов) был доступен **вообще без токена** — то есть любой человек в интернете, зная адрес твоего сайта, мог скачать все заявки. Теперь весь `/api/orders/*` (кроме самой отправки формы) требует авторизации.
- Скачивание файлов (`/api/orders/:id/file`) тоже теперь требует токен.
- Смена статуса и удаление заявок — тоже под авторизацией.
- Публичным (без токена) остался только один эндпоинт — `POST /api/orders`, то есть сама отправка заявки с сайта, как и должно быть.

## Перед хостингом — краткий чек-лист (не изменился)

- `DATABASE_URL` — реальный Postgres, иначе данные пропадают при перезапуске.
- `STORAGE_DRIVER=s3` + заполненные `S3_*` — если хостинг с эфемерным диском.
- `JWT_SECRET` — замени на длинную случайную строку.
- Токен Telegram-бота — лучше перевыпустить у @BotFather, раз он уже "погулял" в переписке.
- Сразу после первого запуска в проде — смени пароль `admin` через раздел "Сменить свой пароль".
